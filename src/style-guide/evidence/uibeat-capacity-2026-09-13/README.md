# UIBeat whole-scene capacity capture

This directory prepares the remaining UIBeat capacity gate without changing the accepted consumer distribution or source architecture. The capture compares the same sounding production scene with UIBeat on, off, then on again. It records foreground-tab frame callback intervals, Chromium performance-counter deltas, Long Animation Frame entries, and selected browser-pipeline trace events. Each short diagnostic trace follows its untraced frame-callback window so trace collection does not contaminate the primary pacing sample. Selected raw trace events are stored in a gzip sidecar with its SHA-256 in the verification report; event-name counts remain inline for review.

These sources answer different questions:

- `requestAnimationFrame` intervals show how often the foreground page receives an animation opportunity while the whole production scene runs. Each callback arrival is timestamped before the harness performs its validation reads. The first interval begins at sample start, so an initial stall is retained, and samples with fewer than two callbacks or less than the requested coverage are invalid. These primary intervals and Long Animation Frame entries cover the untraced pacing window only. Bounded MutationObservers record distinct inline `scale` changes for every visible UIBeat control and recurring `transform`/`opacity` changes for the four production BeatIndicator children throughout each pacing-plus-trace window. A separate validation rAF and retained-state observer continue through the trace and catch temporary state changes or node loss even when the scene recovers before its final snapshot. The retained control and indicator nodes must remain connected, visible, and in the expected state through `on -> off -> on`; the indicator must keep changing during on windows and remain unchanged while off. Every control target and the indicator as a whole must avoid a start, middle, or end idle gap longer than two beat periods, with a conservative 2-second floor. Each indicator child must also avoid an idle gap longer than one complete four-beat cycle, with the same floor. Each primary pacing window must span at least two applicable allowances. This rejects retained `running` attributes, briefly active clocks or individual indicator children that freeze, and captures too short to demonstrate sustained cadence. The MutationObservers plus per-frame retained-node identity, connection, binding, state, and visibility checks add main-thread and layout observation work after each arrival timestamp and continue during tracing; they can affect subsequent measured pacing and trace workload. Neither signal proves that a hardware panel displayed every callback.
- Long Animation Frame and CDP performance counters attribute main-thread script, style, and layout work. They are diagnostic data, not whole-frame presentation evidence by themselves.
- CDP trace events expose browser compositor/presentation stages where the browser build reports them. They still do not independently observe physical display scanout.
- A capacity-closing result therefore also requires a named physical device, usable and unchanged non-software WebGL renderer/vendor identities at both endpoints, a stable available display fingerprint, its native browser window visibly foregrounded for the full run, native viewport/display metadata, and affirmative structured operator verdicts including that the window stayed on the same panel and display mode. Software rendering, Xvfb, headless browsers, emulated viewports, missing renderer identity, and adverse or unknown operator verdicts stay explicitly ineligible.

## Physical capture procedure

The harness requires Node.js 22 or newer with the built-in global `fetch` and `WebSocket` APIs. It checks these prerequisites before opening metadata or contacting Chrome and reports the detected runtime when they are missing. The checked development host runs Node.js 24.13.1 with both APIs available.

1. Check out the exact revision under test with a clean worktree. Follow [the build identity procedure](./build-identity.md): run `node src/style-guide/evidence/uibeat-capacity-2026-09-13/build-identity.mjs`, then serve that exact `dist` directory with its generated manifest on port `5183`. Put the helper's full printed revision in metadata `sourceRevision`. A hosted deployment is usable only when it serves its own matching build identity manifest; an older deployment without one fails verification.
2. Open production in a dedicated native Chrome profile on the named physical desktop or phone. Keep the window and tab visible, unobscured, focused, and awake for the entire capture. Do not resize it between samples.
3. Expose that existing Chrome session through a local CDP endpoint. On Android this can be an `adb forward` to Chrome's debugging socket; on desktop use the browser's supported remote-debugging launch route. Keep exactly one page target in the dedicated browser profile. The harness rejects any additional page, even when it does not match `--target`, and monitors page creation, destruction, and navigation throughout measurement so browser-wide trace events cannot be attributed to another page. Do not substitute device emulation or a virtual display.
4. Copy `metadata.example.json`, fill every field from the actual device and display, including pre-run power, thermal, and operator observations. Keep `evidenceClass` as `physical-native-visible` only when the conditions above are true.
5. Run:

   ```sh
   node src/style-guide/evidence/uibeat-capacity-2026-09-13/capture.mjs \
     --cdp http://127.0.0.1:9222 \
     --target emotitone \
     --metadata /tmp/uibeat-device.json \
     --output src/style-guide/evidence/uibeat-capacity-2026-09-13/<device>-verification.json
   ```

Before scene preparation, the script matches the measured page's loaded entry HTML and CSS content plus exact-URL JavaScript executed in the main frame's default context to the clean-build manifest. It then refuses a hidden or unfocused document, begins interruption monitoring before scene preparation, starts a five-note sounding production pattern when playback is not already running, opens Config without closing an already-open panel, explicitly selects Global, and records equal-duration on/off/on windows. When it finds existing playback, it reuses and records that scene rather than pretending it created a fresh one. It records blur, focus, visibility, and resize events across scene preparation, pacing, warmup, trace, and restoration; includes the initial animation-frame delay; and drains queued terminal long-frame/task entries. A session-long runtime guard synchronously subscribes to the source Pinia workload stores and observes semantic CodeStrip and control mutations, retaining changes even when the operator restores the original value before a boundary snapshot. It covers warmups, pacing windows, traces, and UI Rhythm restoration; only `uiBeat.isEnabled` is omitted because the harness intentionally toggles it. Each pacing-plus-trace window also requires recurring successful full-canvas clears through the retained production Stage 2D context, with no leading, internal, or trailing gap above one second. Canvas/context replacement, disconnection, context loss, a stopped draw loop, or any recorded CodeStrip, performance control, instrument, Global Config, master Visuals, or effective rendering configuration change invalidates capture. The effective configuration includes transient Stage Look patches. Capture fails if the source-coupled runtime stores or Stage canvas cannot be inspected. These subscriptions, the semantic DOM observer, and the Stage `clearRect` heartbeat wrapper add bounded observation overhead. Expected consumers come from the visible source contracts: enabled, non-loading Button faces; Knob faces except `isDisabled` wrappers; every Joystick beat face; and only the selected InstrumentSelector Sticker. The harness rejects an expected owner with no visible target, then retains those exact nodes from the first on window through the full sequence. Each on window requires them to remain bound, running, visible, and changing scale, with the same per-family inventory at both boundaries and across both on windows. The off window requires the same nodes to remain visible and unbound with no inline scale writes. The harness releases those temporary references when monitoring ends, restores the original UI Rhythm value, and fails finalization if restoration or runtime-guard cleanup fails alongside any earlier capture error. It inspects both initial and final renderer identities, rejects missing or changed identities, and rejects known software-renderer names even without a matching trace event. Use a dedicated profile because the app persists configuration locally.

For a `physical-native-visible` capture, the command pauses after measurement for explicit yes/no verdicts covering full-run visibility and occlusion, physical-display interruptions, visible stutter, acceptable final thermal state, and whether the window remained on the same physical panel and display mode, followed by a narrative. The raw answers are retained even when adverse or unknown; eligibility requires affirmative visibility, thermal, and same-panel/display-mode verdicts and negative interruption and stutter verdicts. This fresh post-run observation is included before eligibility and report hashing. A physical run cannot finalize unattended. Software-rendered and emulated rehearsals remain unattended because they are never eligible for closure.

Review the result rather than treating `capacityClosureEligible: true` as an automatic verdict. Compare both on windows against the middle off window, inspect all raw intervals and long-frame entries, confirm the accepted consumer counts, and account for device refresh rate, thermal state, power mode, browser warnings, and visible interruptions. A physical desktop result and a physical mobile result are both required by the current gate.

Consumer counts are recorded by current source family and by viewport visibility. They describe the exact captured scene; an older receipt may have had different panels or controls open.

## Current evidence status

The committed `software-rendered-verification.json` exercises this procedure in a visible Xvfb Chrome window. It is useful for validating the capture path and checking for a gross UIBeat regression. It cannot close the named physical-device or native displayed-frame gate. Reports captured before the post-run-observation schema remain legacy rehearsal evidence and are not eligible for physical closure.
